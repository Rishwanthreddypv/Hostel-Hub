HOSTEL HUB — VERIFIED END-TO-END PROJECT EXPLANATION
====================================================

Purpose of this document
------------------------
This document describes the Hostel Hub project as it is implemented in the
current source code. It is intended to be given to another ChatGPT session or a
diagramming tool as the factual source for a complete architecture diagram.

The description was prepared by inspecting the frontend source, Express API,
business-rule modules, database adapter, schema migrations, CSV importer,
configuration, tests, and audit scripts. Features listed under “Not implemented”
must not be shown as active components in an architecture diagram.


1. SYSTEM PURPOSE
=================

Hostel Hub is a local full-stack hostel discovery and booking application for
three roles:

1. Resident/User
   - Registers or signs in.
   - Searches approved hostels and room inventory.
   - Applies filters and sorting.
   - Uses map view, wishlist and comparison.
   - Contacts hostel owners through in-app messages.
   - Requests one to four beds for a date range.
   - Waits for owner approval.
   - Completes a simulated payment.
   - Downloads a receipt.
   - Cancels a booking and views the server-calculated refund.
   - Reviews an eligible stay.
   - Receives notifications and creates support requests.

2. Hostel Owner
   - Has an independent login stored in the common users table.
   - Can own and manage one or more hostel properties according to plan limits.
   - Manages property information, room types, bed capacity, rent and photos.
   - Uploads private verification documents.
   - Submits listings for admin verification.
   - Views only bookings, messages, payments and analytics connected to the
     owner’s properties.
   - Approves or rejects booking requests.
   - Marks eligible stays completed.
   - Uses either the Basic or Advanced plan.

3. Administrator
   - Uses an admin account that cannot be created through public registration.
   - Reviews submitted hostel listings and private documents.
   - Approves or rejects listings with a note.
   - Suspends or reactivates non-admin accounts.
   - Moderates reviews.
   - Resolves support complaints.
   - Processes simulated refunds.
   - Views platform-wide hostels, users, bookings, payments, subscription
     attempts, analytics, import history and audit history.

This project is a working local demonstration. Booking payments, subscription
payments and refunds are simulations. No real money is transferred.


2. IMPLEMENTED TECHNOLOGY STACK
===============================

Frontend
--------
- React 19.
- TypeScript 5.
- React Router 7.
- Vite 7 for development and production builds.
- Leaflet for OpenStreetMap rendering.
- Lucide React for icons.
- A project-specific responsive CSS file; no separate UI framework is used.

Backend
-------
- Node.js 24 or newer.
- Express 5.
- Zod for request validation.
- bcryptjs for password hashing.
- jsonwebtoken for signed session tokens.
- cookie-parser for the session cookie.
- express-rate-limit for API and login limits.
- Helmet for HTTP security headers and Content Security Policy.
- Multer with memory storage for validated uploads.

Database
--------
- The current local installation is configured to use MySQL database
  “hostel_hub” through mysql2/promise and DATABASE_URL.
- The code also implements SQLite through Node’s built-in node:sqlite module.
- An explicit SQLite path is used by automated tests so tests do not inherit the
  live MySQL connection from .env.
- Both engines are accessed through the same small adapter with all(), get(),
  run(), transaction(), lock and close operations.

Storage and external resources
------------------------------
- Public listing photos are stored under uploads/.
- Private verification documents are stored under uploads/private/.
- Bundled sample images and fonts are under public/.
- The browser loads map tiles from OpenStreetMap.
- A listing can open an external Google Maps search link.
- An OpenAI-compatible assistant provider is optional. Without AI credentials,
  the implemented local database-search assistant is used.

Testing
-------
- Node’s built-in test runner.
- Supertest for Express API tests.
- Playwright with Microsoft Edge for browser workflows.
- Dedicated scripts for live MySQL API, browser, UI-surface and integrity audits.


3. HIGH-LEVEL RUNTIME ARCHITECTURE
==================================

Normal production-style local start
-----------------------------------
1. npm start executes server/index.js.
2. server/index.js loads environment variables.
3. createDatabase() selects MySQL or SQLite from configuration.
4. The database adapter creates missing base tables and runs additive migrations.
5. Outside production, when DEMO_MODE is not false, seed() ensures bootstrap demo
   accounts exist and imports CSV data only when a successful import does not
   already exist. A forced seed command can apply reviewed source changes.
6. createApp() builds the Express application and installs middleware and routes.
7. Express listens on HOST, default 127.0.0.1, and PORT, default 4000.
8. If dist/ exists, Express serves the compiled React single-page application.
9. Requests for unknown frontend routes return dist/index.html so React Router can
   resolve the client route.
10. SIGINT or SIGTERM closes the HTTP server and database connection cleanly.

Development start
-----------------
- npm run dev starts two processes with concurrently:
  1. Node/Express on port 4000 with file watching.
  2. Vite on 127.0.0.1:5173.
- Vite proxies /api and /uploads to 127.0.0.1:4000.
- In the built application, browser, API and uploads share the Express origin.

Browser-to-server communication
-------------------------------
- src/api.ts contains the shared api() wrapper.
- Requests are sent to /api plus the requested path.
- credentials: include sends the HTTP-only session cookie.
- Mutation requests include X-HostelHub-Client: web.
- JSON payloads use Content-Type: application/json.
- Upload payloads use FormData and multipart/form-data.
- Non-success responses are converted to JavaScript Error objects using the
  backend’s JSON error message.

5. BACKEND APPLICATION ARCHITECTURE
===================================

5.1 Express construction and middleware
---------------------------------------
Main file: server/app.js

createApp(db, options) configures:

1. Demo/production behavior
   - Demo mode defaults on only outside production unless overridden.
   - Production requires a JWT_SECRET of at least 32 characters.
   - Without a configured secret in development, a random secret is generated;
     sessions therefore do not survive a process restart unless JWT_SECRET is set.

2. Upload directories
   - Creates uploads/ and uploads/private/ when missing.

3. Helmet
   - Disables x-powered-by.
   - Sets a Content Security Policy.
   - Allows local scripts/connections, inline CSS required by the app,
     OpenStreetMap image tiles and Google frame origin.

4. Body and cookie parsing
   - JSON body limit: 1 MB.
   - Cookie parser.

5. Mutation request protection
   - POST/PATCH/DELETE-like mutations require X-HostelHub-Client.
   - If Origin is present, it must match configured APP_ORIGIN, approved local
     Vite origins or the request’s own host origin.

6. Rate limiting
   - General /api limit: 300 requests per 60 seconds per limiter identity.
   - Login/register limiter: 40 requests per 15 minutes.
   - Assistant limiter: 15 requests per 60 seconds.

7. SQLite serialization
   - When the selected client is not MySQL, API requests are serialized around
     the single SQLite connection to avoid interleaved asynchronous writes.

8. Session restoration
   - Reads hh_session from an HTTP-only cookie.
   - Verifies HS256 JWT.
   - Loads the user from the database on every authenticated request.
   - Requires active account status.
   - Requires JWT token version to match users.token_version.

9. Role middleware
   - auth() requires any signed-in user.
   - auth("user"), auth("owner") or auth("admin") requires the named role.

10. Error handling
    - Zod errors return 400.
    - Multer errors return 400.
    - Application errors use their defined HTTP status.
    - Duplicate/unique failures return 409.
    - Unexpected errors are logged server-side and return a generic 500 response.

5.2 Session and account behavior
--------------------------------
- Public registration accepts name, email, password, role=user/owner, identity
  document type, consent and one JPEG, PNG or PDF identity document up to 5 MB.
- Email is normalized to lowercase.
- Password length is 10 to 72 characters.
- Password is hashed with bcrypt cost 12.
- Duplicate email returns conflict.
- The account and identity metadata are inserted transactionally with user
  status=pending_verification and verification status=pending.
- Identity files use generated names under uploads/private and are not exposed
  by the public /uploads route.
- Active admins receive a stored notification about the new review.
- Registration does not issue a session cookie.
- Login compares the bcrypt hash and permits only active accounts. Pending,
  rejected and suspended accounts receive status-specific errors.
- Rejected applicants can authenticate only to the public resubmission endpoint,
  replace the private document and return to the pending review queue.
- Admin approval changes the account to active; rejection changes it to rejected
  and records a required review note. Both actions are audited.
- Session JWT expires after 12 hours.
- Cookie is HttpOnly, SameSite=Strict, path=/ and Secure in production.
- Logout increments users.token_version, invalidating existing tokens.
- Password change verifies the old password, stores a new bcrypt hash, increments
  token_version and clears the cookie.
- Admin suspension also increments token_version, revoking active sessions.
- Password hashes and token_version are removed from API user responses.

7. HOSTEL DISCOVERY BUSINESS RULES
==================================

Public inventory conditions
---------------------------
- A hostel must have status=approved.
- Its owner must have status=active.
- Unpublished or inactive-owner hostels are excluded from public search.
- The hostel owner and admin can inspect unpublished detail through an
  authenticated request.

Searchable text
---------------
Every word of the text query must appear in the combined lowercase string of:
- hostel name,
- city,
- area,
- nearby text.

Filters
-------
- Gender exact match.
- Facilities: every requested facility must be present.
- Budget: at least one room’s discounted rent must be within budget.
- Sharing: at least one room has the requested sharing value.
- AC: at least one room has the requested AC flag.
- Availability: when dates are supplied, at least one room has available beds.
- Rating: published-review average meets minimum.
- Distance: backend calculates Haversine distance using supplied latitude and
  longitude and optionally filters by maximum kilometres.

Sorting
-------
- price-low: minimum room rent ascending.
- price-high: minimum room rent descending.
- rating: rating descending.
- recommended/default: owner plan search priority, then discount, then rating.
- Advanced has higher plan search priority than Basic.

Availability calculation
------------------------
- Date intervals are treated as [start_date, end_date), allowing reuse on the
  move-out date.
- Occupancy is calculated as a quantity-weighted sweep of booking start/end
  events.
- Confirmed reservations occupy capacity.
- Active flow-version-2 pending-owner and awaiting-payment holds occupy capacity
  only before expires_at.
- Expired unpaid holds release capacity without requiring a scheduled job.


8. OWNER PROPERTY AND VERIFICATION FLOW
=======================================

Listing lifecycle
-----------------
1. A registered owner creates a listing.
2. Creation requires at least one room type.
3. Listing begins with status=draft.
4. Owner uploads public photos.
5. Owner uploads at least one private verification document.
6. Submission checks that at least one photo and document exist.
7. Listing changes to pending.
8. Active admins receive a notification.
9. Admin can approve or reject only a pending listing.
10. Approval is blocked if no document exists.
11. Approved listing is visible in public search.
12. Rejection stores the admin note and notifies the owner.
13. A material listing edit resets status to draft and clears the verification
    note, requiring resubmission.

Owner isolation
---------------
- Owner property queries use owner_id=req.user.id.
- The owned() helper returns not found when the listing is missing or belongs to
  another owner.
- Room operations first identify the room’s hostel and then verify ownership.
- Private document download permits only the recorded document owner or admin.
- Booking lists and portfolio queries join through hostels.owner_id.

Room capacity updates
---------------------
- Room capacity is a number of beds for a room type, not physical-room count.
- Before reducing capacity, the backend calculates peak quantity across future
  active reservations.
- New capacity cannot be lower than the existing reservation peak.

Upload handling
---------------
- Multer memory storage accepts one file with maximum size 8 MB.
- The backend checks file signatures, not only browser MIME labels.
- Public photo types: JPEG, PNG, WebP.
- Private document types: PDF, JPEG, PNG, WebP.
- Public photo filenames are generated UUIDs.
- Public /uploads route accepts only generated image filename patterns.
- uploads/private is not exposed through static middleware.
- Private documents are downloaded through the authorized API route with
  Cache-Control: no-store.


9. BOOKING DOMAIN AND STATE MACHINE
===================================

9.1 New booking creation
------------------------
Only role=user can create a booking.

Input:
- room_id,
- start_date,
- end_date,
- quantity from one to four beds,
- optional guest_note up to 1,000 characters.

Validation:
- Move-in cannot be before the current UTC calendar date.
- Move-out must be after move-in.
- Stay must be between 7 and 366 nights.
- The listing’s own minimum stay must also be satisfied.
- Room must exist.
- Hostel must be approved.
- Owner must be active.
- Available capacity must cover the requested quantity.
- The same user cannot create an overlapping active booking at the same hostel.

Concurrency:
- Booking creation runs in a database transaction.
- MySQL appends FOR UPDATE when loading the room, locking it during capacity
  validation and insert.
- SQLite uses BEGIN IMMEDIATE and API serialization around its single connection.
- This prevents concurrent last-bed overselling in the supported local model.

9.2 Server-side price snapshot
------------------------------
The browser does not send trusted totals.

For requested quantity Q:
- gross monthly rent = room rent per bed × Q.
- discount amount = rounded gross rent × hostel discount percentage.
- discounted monthly rent = gross rent − discount amount.
- deposit = hostel deposit per bed × Q.
- food charge = hostel monthly food charge per bed × Q.
- service charge = hostel service charge per bed × Q.
- tax = rounded percentage of discounted rent + food + service.
- total initial payment = discounted rent + deposit + food + service + tax.

These values are copied into the booking row so later listing price changes do
not change the existing booking quote.

The initial payment covers the first month and deposit/fees. The application
does not automatically collect subsequent monthly rent.

9.3 New flow-version-2 state transitions
----------------------------------------

Initial state:
- pending_owner.
- A 24-hour request deadline is stored in expires_at.
- A booking event is written.
- The owner is notified.

pending_owner can transition to:
- awaiting_payment when the correct owner approves.
  - approved_at is stored.
  - A fresh 24-hour payment deadline replaces expires_at.
- rejected when the correct owner rejects with a reason of at least five
  characters.
  - No payment exists and refund is zero.
- cancelled when the resident cancels before payment.
  - Refund is zero.
- derived expired when expires_at passes.

awaiting_payment can transition to:
- confirmed after a successful simulated payment.
- cancelled when resident cancels before payment; refund zero.
- derived expired when payment deadline passes.
- It remains awaiting_payment after a failed simulated payment so retry is
  possible while the window remains valid.

confirmed can transition to:
- completed when the owning owner marks it complete on or after move-out.
- refund_pending when the resident cancels a paid booking.

refund_pending can transition to:
- refunded when an admin processes the supported demo refund.

9.4 Legacy compatibility
------------------------
- Existing flow-version-1 bookings are intentionally preserved.
- They retain their older payment-before-owner-approval transition.
- The legacy POST /bookings/:id/pay route handles those records only.
- Newly created bookings always use flow_version=2 and the approval-before-
  payment flow described above.

9.5 Booking actions and stale-decision protection
-------------------------------------------------
POST /bookings/:id/action accepts:
- action: approve, reject, cancel, complete or refund.
- optional reason.
- optional expected_status.
- optional expected_refund_amount.

The UI fetches the latest booking detail before confirmation and sends expected
status/refund preconditions. If state or amount changed, the API returns 409 and
the transaction rolls back. Older clients may omit preconditions, but server
authorization, state checks and calculated amounts still apply.

9.6 Booking history
-------------------
- booking_events is append-only application history for implemented actions.
- Events store booking ID, actor ID, actor name, actor role, event, resulting
  status, optional note and timestamp.
- Event insertion occurs in the same transaction as the corresponding booking
  state or payment change.
- Existing historical actions from before the table was introduced are not
  fabricated.
- Booking detail is visible only to that resident, the property owner or admin.


10. PAYMENT AND REFUND ARCHITECTURE
===================================

10.1 Payment attempts
---------------------
Module: server/payments.js

Only the booking resident can start an attempt.

Input:
- method: upi, card or netbanking.
- outcome: success or failure.
- idempotency_key: UUID.

Rules:
- Demo mode must be enabled.
- Booking must currently be awaiting_payment.
- Booking deadline must not have expired.
- No final payment may already exist.
- If a processing attempt already exists for the booking, it is returned.
- Reusing the same idempotency key with the same request returns the earlier
  attempt.
- Reusing it for a different booking/user/method/outcome returns conflict.

Created attempt:
- status=processing.
- amount copied from booking total.
- ready_at is approximately 1.5 seconds after creation.
- payment_started event is recorded.

Completion:
- Locks and reloads the attempt and booking.
- Returns an already-final attempt unchanged.
- Returns processing if ready_at has not arrived.
- Becomes expired if the booking is no longer payable.
- Becomes failed for selected failure outcome.
- Becomes paid for selected success outcome.

Successful completion:
- Inserts exactly one payments row because booking_id is unique in payments.
- kind=booking.
- status=paid.
- provider=demo.
- method is stored.
- A generated HH- reference is stored.
- Version-2 booking becomes confirmed.
- Payment event and resident/owner notifications are written.

10.2 Role-scoped payment ledger
-------------------------------
- Resident sees payments with p.user_id=current user.
- Owner sees booking payments for owned hostels and subscription payments paid
  by that owner.
- Admin sees all payments.

10.3 Booking receipt
--------------------
- Generated dynamically as an HTML file.
- Accessible only to booking resident, property owner or admin.
- Includes reference, date, guest, property, room, bed quantity, stay dates,
  payment method, rent, deposit, food, service, tax, discount, amount, payment
  status and processed refund amount.
- States that it is a demo payment and not a tax invoice.

10.4 Cancellation and refunds
------------------------------
Unpaid pending/awaiting-payment cancellation:
- No payment was received.
- Refund amount is zero.
- Reserved capacity is released.

Paid cancellation before move-in:
- Refund quote equals the full initial payment.

Paid cancellation on or after move-in:
- Refund quote equals the captured deposit.
- Rent is retained.

Admin refund:
- Allowed only for refund_pending booking.
- Allowed only when payment provider is demo.
- Changes payment status to refunded and records refunded_at.
- Changes booking status to refunded.
- Does not contact a real financial provider.

Dashboard/portfolio net collections subtract the booking’s processed
refund_amount from paid amount for refunded rows.


11. BASIC AND ADVANCED PLAN ARCHITECTURE
========================================

Authority file: server/plans.js

Basic
-----
- Price: INR 0.
- Maximum properties: 1.
- Maximum photos per property: 8.
- Search priority: 0.
- Advanced analytics: false.
- Booking report export: false.
- Special offers/discount creation: false.

Advanced
--------
- Simulated price: INR 999.
- Maximum properties: 10.
- Maximum photos per property: 200.
- Search priority: 1.
- Advanced analytics: true.
- Booking report export: true.
- Special offers/discount creation: true.

Plan enforcement points
-----------------------
- Property creation quota.
- Per-property photo additions.
- Discount/special-offer creation or increase.
- Recommended public-search priority.
- Property-level portfolio analytics.
- Owner booking CSV export.
- Frontend control states and plan descriptions through /api/config.
- CSV dataset validation.

Advanced simulated checkout
---------------------------
- Owner starts subscription_attempt with method, selected success/failure outcome
  and UUID idempotency key.
- Status begins processing for about 1.5 seconds.
- Failed completion leaves the account on Basic.
- Successful completion:
  - updates users.plan to Advanced,
  - inserts a common payments ledger row with booking_id=NULL,
  - kind=subscription,
  - plan_code=Advanced,
  - amount=999,
  - status=paid,
  - provider=demo,
  - generated PLAN- reference,
  - notification and audit entries.
- Owner or admin can download a plain-text demo subscription receipt.

Downgrade behavior
------------------
- POST /owner/subscription accepts Basic downgrade only.
- Existing properties, photos, rooms, bookings and history are preserved.
- Processing subscription attempts are cancelled.
- Basic rules apply to future additions.
- If an owner already has more than one property, those listings remain; the
  owner cannot create another property while above the Basic maximum.
- Existing photos above the Basic maximum may remain or be reduced, but new
  photos cannot be added while still above the maximum.
- An existing discount may remain or be reduced, but a Basic owner cannot create
  or increase an offer.

There is no automatic renewal, expiry period, recurring billing or real payment
provider for plans.


12. REVIEWS, MESSAGES, NOTIFICATIONS AND SUPPORT

Reviews
-------
- Only role=user can submit.
- Booking must belong to the user.
- Booking must be confirmed or completed.
- Move-in date must have arrived.
- One review per booking is enforced by a unique booking_id.
- Rating range is 1 to 5.
- New reviews are published immediately.
- Admin can change status between published and hidden.
- Public averages/details use published reviews only.

Messages
--------
- Every message is connected to one hostel.

- An owner can reply only to a guest who previously messaged that owner about
  that hostel.

- Sending a message creates a recipient notification.

Notifications

- Stored in MySQL/SQLite, not pushed through email/SMS.
- Scoped by user_id.
- Read state is is_read.
- Used for registration, booking requests, decisions, payments, listing review,

- Frontend polls rather than using WebSockets.

Complaints/support
------------------
- Signed-in users can create requests.
- Optional booking_id is accepted only if that booking belongs to the requester.
- Non-admins list only their own complaints.
- Admin lists all complaints.
- Admin resolution changes status to resolved, stores resolution text, notifies
  the requester and writes an audit entry.

Audit log
---------
- Stores actor_id, action, target_id, detail and timestamp.
- Used for booking actions, plan events, listing decisions, user status changes,
  review moderation and complaint resolution.
- It is an application audit history, not an external observability service.

14. DATABASE ARCHITECTURE
=========================

14.1 Database adapter
---------------------
File: server/db.js

MySQL:
- mysql2/promise connection pool from DATABASE_URL.
- Prepared execute calls with parameter arrays.
- Transactions acquire a pool connection, begin, commit/rollback and release.
- lock property is “ FOR UPDATE”.

SQLite:
- Node DatabaseSync.
- WAL journal mode.
- Foreign keys enabled.
- Busy timeout 5,000 ms.
- BEGIN IMMEDIATE transaction.
- Writes are queued around the shared connection.

The adapter exposes the same asynchronous interface for both engines.

CSV parser

File: server/csv.js

- Implements RFC-4180-style quoted fields.
- Handles commas, escaped quotes, CRLF, multiline values and UTF-8 BOM.
- Rejects malformed quotes, wrong column counts and duplicate/missing headers.
- stringifyCSV emits quoted UTF-8-with-BOM content.

Validation
----------
File: server/seed-import.js

Before import it verifies:
- Manifest version, synthetic flag and reference date.
- Exact documented columns for every file.
- Numeric types and bounds.
- Enum values.
- Stable identifier syntax.
- Required fields.
- ISO timestamps and YYYY-MM-DD dates.
- .test domain for synthetic accounts.
- Coordinates, discounts, tax and minimum stay.
- Room sharing, rent, capacity and AC values.
- Review rating.
- Bundled photo paths and generated sample document paths.
- Foreign-key-style relationships across all CSVs.
- Property belongs to an owner.
- Room belongs to booking hostel.
- Booking belongs to a resident.
- Booking amounts reconcile.
- Payment amount matches booking total.
- Review eligibility.
- Messages include the property owner.
- Subscription payment belongs to an Advanced owner and is INR 999.
- Account emails are unique.
- Basic/Advanced property, photo and discount rules.
- One final payment/review per booking in seed data.
- Paid booking states have a payment; unpaid states do not.
- Refund states match.
- Overlapping seeded bookings do not exceed room capacity.

Import behavior
---------------
- Import is disabled when NODE_ENV=production.
- Seed dates are shifted relative to the first import anchor date.
- Normalized hostel facilities and photos are assembled into JSON strings.
- Subscription CSV rows are added to the common payments table with
  booking_id=NULL and kind=subscription.
- Seed passwords are bcrypt hashes of DEMO_SEED_PASSWORD or the documented local
  default.
- Fictional text declarations are generated in uploads/private when missing.
- All database writes for a successful import occur in one transaction.
- A successful or failed seed_imports row records the outcome.

Live-edit preservation
----------------------
- Each imported row has source and applied hashes in seed_records.
- If a managed row is unchanged in the application and source CSV changed, only
  users, hostels, rooms and documents are eligible for update.
- If the live row differs from the last applied hash, it is preserved.
- Runtime/financial history is treated as immutable through repeat seed imports.
- A room with active reservations is not overwritten.
- Missing rows are inserted.
- Repeat imports are therefore idempotent and avoid overwriting live changes.

19. COMPLETE END-TO-END USER FLOWS
==================================

19.1 Resident discovery and booking
-----------------------------------
1. Browser loads React SPA from Express or Vite.
2. App requests config and optional current session.
3. Explore requests GET /api/hostels with URL query filters.
4. Express validates query parameters.
5. API queries approved hostels owned by active accounts.
6. API loads room inventory, calculates availability and published rating.
7. API applies text, facility, room, rating, distance and plan-priority rules.
8. React displays cards or Leaflet map.
9. Resident opens detail and chooses room, quantity and dates.
10. POST /api/bookings validates all inputs.
11. Transaction locks the room in MySQL, rechecks capacity and calculates price.
12. Booking and initial timeline event are inserted.
13. Owner receives stored notification.
14. Resident sees pending_owner.
15. Owner approves; booking becomes awaiting_payment with fresh deadline.
16. Resident opens Checkout.
17. Payment-attempt endpoint creates processing attempt with UUID idempotency.
18. Completion simulates failure or success.
19. Failure is stored as an attempt and can be retried.
20. Success inserts final payment and changes booking to confirmed.
21. Resident and owner receive notifications.
22. Resident downloads server-generated HTML receipt.

19.2 Cancellation and refund
----------------------------
1. Resident opens current booking detail.
2. Server returns current cancellation quote and allowed cancel action.
3. UI shows refund amount and explanation.
4. UI posts cancel with expected state and expected amount.
5. Transaction rechecks both values.
6. Unpaid booking becomes cancelled with zero refund.
7. Paid booking becomes refund_pending with full-payment or deposit refund based
   on the current date.
8. Admin opens refund queue.
9. Admin posts refund action.
10. Backend verifies demo provider and pending state.
11. Payment becomes refunded, booking becomes refunded, events/audit and
    notifications are stored.

19.3 Account identity verification
----------------------------------
1. Applicant chooses resident or owner and enters name, email and password.
2. Applicant selects an identity type, confirms consent and uploads a fictional
   JPEG, PNG or PDF document no larger than 5 MB.
3. Backend validates fields, file signature and size.
4. Backend hashes the password, writes the private file under a generated name,
   and transactionally creates the pending account and verification record.
5. Active admins receive a notification; the applicant receives no session.
6. Pending login is blocked with an awaiting-approval message.
7. Admin opens Account verification, downloads the document through the
   role-protected endpoint and enters a required review note.
8. Approval changes the account to active, stores reviewer/time, notifies the
   applicant and writes an audit event. The applicant can then sign in.
9. Rejection changes the account to rejected and exposes the reason at login.
10. The applicant submits the same email/password with a replacement document.
11. Backend locks the records, deletes the superseded private file after commit,
    clears the prior decision and returns the account to pending_verification.

19.4 Owner listing verification
-------------------------------
1. Owner registers or signs in.
2. Owner creates listing and first room; backend checks plan quota.
3. Listing is stored as draft.
4. Owner uploads generated-name public image.
5. Owner uploads private PDF/image verification document.
6. Owner submits listing.
7. Backend requires a photo and document and marks pending.
8. Admin receives notification.
9. Admin dashboard loads listing and document metadata.
10. Admin downloads document through protected API.
11. Admin approves or rejects with note.
12. Backend changes status, notifies owner and writes audit entry.
13. Approved listing appears in public search.
14. Later material edit returns it to draft.

19.5 Advanced plan activation
-----------------------------
1. Basic owner opens /owner/plans.
2. Frontend receives both plan definitions from /api/config.
3. Owner chooses Advanced and a simulated method/outcome.
4. API creates processing subscription_attempt with UUID idempotency.
5. Frontend waits and calls completion.
6. Failure stores failed attempt; Basic remains unchanged.
7. Retry uses a new UUID.
8. Success changes users.plan to Advanced and creates subscription payment.
9. Notification and audit entry are created.
10. Frontend refreshes session user and unlocks Advanced controls.
11. Owner can download text receipt.

19.6 CSV to MySQL
-----------------
1. Administrator/developer edits synthetic CSV files.
2. npm run db:validate parses every file and validates full relationships without
   opening/writing a database.
3. npm run db:seed connects to the configured database.
4. Data is reparsed and revalidated.
5. Dates are rebased to the preserved anchor.
6. Rows are normalized for database tables.
7. Source/applied hashes are compared.
8. New rows are inserted.
9. Eligible unchanged managed records can receive source updates.
10. Live edits and financial history are preserved.
11. All accepted writes commit in one transaction.
12. Import summary is stored and visible to admin portfolio.

21. EXPLICITLY NOT IMPLEMENTED
==============================

Do not draw any of the following as active production components:

- No live Razorpay or other payment gateway.
- No real card processing, UPI transfer or net-banking connection.
- No payment-provider webhooks or provider reconciliation.
- No automatic recurring plan billing.
- No subscription expiry or billing periods.
- No automatic monthly hostel-rent collection after the first payment.
- No email delivery service.
- No SMS or WhatsApp delivery.
- No WebSocket or push-notification server.
- No Redis cache, Redis session store or distributed rate limiter.
- No message queue, event bus, Kafka or RabbitMQ.
- No microservices; this is one Express application.
- No separate owner authentication table; all roles use users.
- No cloud object storage; uploads use local disk.
- No malware scanning service for uploads.
- No paid Google Maps API integration.
- No guaranteed external search-engine visibility.
- No verified real businesses; seed listings and documents are fictional.
- No deployed production monitoring/telemetry platform.
- No horizontal scaling mechanism.
- No full versioned migration/rollback framework.
- No pagination for the small local list/report APIs.
- No mandatory hosted AI service; the default assistant is local search.
