HOSTEL HUB — WORK AND PRESENTATION SPLIT FOR 3 MEMBERS
=====================================================

Purpose
-------
This split gives every member a meaningful frontend, backend, database, testing,
and live-demonstration contribution. Replace “Member 1/2/3” with your names.

Suggested total presentation time: 15–18 minutes
Each member: approximately 5–6 minutes


MEMBER 1 — USER EXPERIENCE, AUTHENTICATION AND HOSTEL DISCOVERY
===============================================================

Main responsibility:
Build and explain the public-facing experience and the user account flow.

Frontend contribution:
- Application routing, navigation, role guards and shared components.
- Registration and login for residents and hostel owners.
- User profile and password-management screens.
- Hostel home page, listing cards and detailed hostel page.
- Search by city, area, hostel and nearby institution.
- Filters for budget, gender, room sharing, AC, food, Wi-Fi, rating,
  availability and distance.
- Sorting, map/list view, Google Maps links and photo/facility display.
- Wishlist, hostel comparison and the local hostel-search assistant UI.
- Responsive public pages and reusable loading, error and empty states.

Primary frontend files:
- src/main.tsx
- src/homes.tsx
- src/account.tsx
- src/shared.tsx
- Relevant public-page sections in src/styles.css

Backend contribution:
- Registration, login, logout and session authentication.
- Password hashing, JWT cookies and role-based authorization.
- Profile update and password-change APIs.
- Public hostel search, filtering, sorting and listing-detail APIs.
- Wishlist, comparison data, user messages and local assistant APIs.
- Input validation, protected routes, CSRF checks and request limits.

Primary backend areas:
- Authentication, public listing, profile, wishlist, message and assistant
  routes in server/app.js
- Shared database access through server/db.js

Database contribution:
- users
- hostels (public discovery fields)
- wishlist
- messages
- notifications used by user-facing flows

Testing contribution:
- Login and registration validation.
- Duplicate email, incorrect password and role-access tests.
- Search/filter/sort tests.
- Wishlist isolation and comparison-limit tests.
- Responsive public-page and protected-route tests.

Suggested speaking points:
1. “Hostel Hub supports three independent roles: resident, owner and admin.”
2. Explain how authentication restores a secure server session and how route
   guards prevent one role from entering another role’s workspace.
3. Show that discovery data comes from MySQL, including room prices,
   facilities, availability, ratings and coordinates.
4. Explain that filters are applied by backend queries, so users cannot bypass
   them by changing the frontend.
5. Demonstrate login, search, filters, map view, details and wishlist.

Live demo segment:
1. Open the home page.
2. Search for a city and apply two or three filters.
3. Open a hostel, view its rooms/facilities/map and save it.
4. Sign in as a resident and open the wishlist/profile.

Handoff line:
“After a resident finds a suitable hostel, the next module takes the request
through approval, payment and booking completion.”


MEMBER 2 — BOOKING LIFECYCLE, PAYMENTS AND RESIDENT–OWNER OPERATIONS
===================================================================

Main responsibility:
Build and explain the complete booking state machine and simulated financial
workflow shared by residents and owners.

Frontend contribution:
- Booking request form with room, date and bed-quantity selection.
- Resident, owner and admin booking workspaces.
- Booking status, attention queues, search, sorting and property filters.
- Owner approval/rejection dialogs and required rejection reasons.
- Payment checkout for UPI, card and net banking.
- Simulated payment decline, retry, processing and success screens.
- Downloadable receipts and payment ledgers.
- Booking timeline, cancellation quote and refund status.
- Portfolio totals for collections, refunds, occupancy and residents.

Primary frontend files:
- src/bookings.tsx
- src/checkout.tsx
- src/portfolio.tsx
- Booking/payment sections in src/styles.css

Backend contribution:
- Server-calculated rent, deposit, food charge, service charge and total.
- Minimum-stay, sharing, quantity and date validation.
- Quantity-weighted availability and overlap checks.
- Transactional capacity protection to prevent overselling.
- Booking state transitions: pending owner, awaiting payment, confirmed,
  rejected, cancelled, refund pending and refunded.
- Owner approval/rejection permissions and payment-window expiry.
- Payment attempts, idempotency, failure/retry and final payment creation.
- Receipt generation, cancellation quote and admin refund processing.
- Booking history events and owner/admin portfolio calculations.

Primary backend files:
- server/booking-workflow.js
- server/payments.js
- server/portfolio.js
- Booking, cancellation and refund routes in server/app.js

Database contribution:
- bookings
- booking_events
- payment_attempts
- payments for booking charges and refunds
- reviews linked to completed bookings

Testing contribution:
- Complete booking → owner approval → payment workflow.
- Failed payment followed by successful retry.
- Duplicate-payment and idempotency protection.
- Concurrent requests and room-capacity protection.
- Cross-owner and cross-user privacy tests.
- Cancellation, refund and downloadable receipt tests.

Suggested speaking points:
1. Explain why pricing is calculated again on the server instead of trusting
   values sent by the browser.
2. Describe the booking state machine and why payment becomes available only
   after owner approval.
3. Explain the transaction used to stop two users from reserving the same last
   bed at the same time.
4. Clarify that the payment experience is realistic but transfers no money.
5. Show how every action is recorded in the private booking timeline.

Live demo segment:
1. Request a hostel as the resident.
2. Sign in as that hostel’s owner and approve the request.
3. Return as the resident, decline one demo payment and retry successfully.
4. Download the receipt and open the booking history.
5. Cancel the booking and show the refund amount/status.

Handoff line:
“The booking workflow depends on owners maintaining verified properties and on
admins controlling trust, plans and refunds, which is covered in the final
module.”


MEMBER 3 — OWNER MANAGEMENT, ADMIN CONTROL, PLANS AND DATA ENGINEERING
=====================================================================

Main responsibility:
Build and explain owner portfolios, listing verification, administration,
subscription plans and the MySQL/CSV data pipeline.

Frontend contribution:
- Owner dashboard, work queues and independent multi-property portfolios.
- Property editor, room management, pricing, facilities and photo uploads.
- Private ownership-document upload and listing submission.
- Admin dashboard for listing approval/rejection and document review.
- User suspension/reactivation, review moderation and complaint handling.
- Payment/refund oversight, audit history and CSV-import history.
- Basic and Advanced plan cards and entitlement display.
- Advanced checkout, failed-payment retry, receipt and Basic downgrade dialog.
- Advanced-only analytics/export controls and Basic quota messages.

Primary frontend files:
- src/management.tsx
- Owner/admin payment and analytics integration in src/portfolio.tsx
- Owner/admin/plan sections in src/styles.css

Backend contribution:
- Owner-scoped property and room CRUD APIs.
- Photo/document validation and private document authorization.
- Listing submission, verification, publication and re-review workflow.
- Admin user, review, complaint, refund and audit APIs.
- Shared Basic/Advanced plan catalogue and enforced entitlements.
- Advanced subscription attempt, completion and receipt APIs.
- Search-priority rules and downgrade data preservation.
- Dashboard statistics, Advanced reports and admin subscription monitoring.
- MySQL connection adapter, schema, migrations and foreign keys.
- Transactional/idempotent CSV import with live-edit preservation.

Primary backend and data files:
- server/plans.js
- Owner, plan and admin routes in server/app.js
- server/db.js
- server/migrations.js
- server/seed-import.js
- server/csv.js
- seed-data/*.csv and seed-data/manifest.json

Database contribution:
- rooms
- documents
- facilities stored with listings
- complaints
- audit_log
- subscription_attempts
- subscription payment rows and plan_code in payments
- seed_records and seed_imports

Testing contribution:
- Independent-owner authorization tests.
- Property/photo quota and discount entitlement tests.
- Advanced upgrade, failure/retry, receipt and Basic downgrade tests.
- Listing verification and private-document tests.
- CSV validation, repeat import and live-edit preservation tests.
- MySQL foreign-key, orphan-record and financial-integrity audits.

Suggested speaking points:
1. Explain that every owner has a separate login and can manage only their own
   properties, rooms, bookings, payments and documents.
2. Demonstrate the verification flow: owner submits documents, admin reviews
   them, and only approved properties appear publicly.
3. Compare the two plans:
   - Basic: 1 property, 8 photos and core management.
   - Advanced: ₹999 simulated payment, 10 properties, 200 photos, priority
     discovery, detailed analytics, report exports and offers.
4. Explain that downgrading never deletes existing owner data; it restricts
   future additions that exceed Basic limits.
5. Describe CSV as editable seed input and MySQL as the live runtime source of
   truth. Registrations, bookings, payments and updates are stored in MySQL.

Live demo segment:
1. Open an owner dashboard and show separate properties and room inventory.
2. Open the plans page and explain Basic versus Advanced.
3. Show the admin verification workspace and subscription/payment statistics.
4. Process the resident’s pending demo refund from Member 2’s segment.
5. Show the MySQL-backed admin analytics or CSV import history.
